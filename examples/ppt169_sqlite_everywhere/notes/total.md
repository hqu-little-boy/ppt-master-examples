# 01_cover

Most of us meet SQLite as the little database in a test suite, so it is easy to file it under toys. The SQLite authors put it differently: think of SQLite not as a replacement for Oracle, but as a replacement for fopen. That one sentence explains almost everything in the next twenty minutes. The drawing behind me is the whole idea in one picture: a single file that opens up into fixed-size pages, starting with page one. Every figure I quote today comes straight from the official documentation on sqlite.org.

---

# 02_most_deployed

Start with the claim that sounds like marketing: SQLite is likely used more than all other database engines combined. The evidence is a list of hosts. It ships in every Android device, every iPhone and iOS device, every Mac, every Windows 10 and 11 installation, and in Firefox, Chrome, and Safari. It is inside every copy of Skype, iTunes, the Dropbox client, TurboTax and QuickBooks; it comes with PHP and Python; and it runs in most television sets, set-top boxes, and car multimedia systems. Now the arithmetic: there are more than four billion smartphones in active use, each holding hundreds of SQLite database files, so there are probably over one trillion SQLite databases in use right now. The project's own best guess is that it is the second most deployed library after zlib, and because it is often statically linked many times per device, it might even be the first.

---

# 03_serverless

Why can it be everywhere? Because there is nothing to deploy. On the left is the model we all know: the application sends SQL over the network to a long-running server process, which owns its data files, and someone has to install, configure, and administer that server first. On the right, SQLite is a library linked into the application's own process, and it reads and writes one ordinary disk file directly. There is no separate server. That single file holds every table, index, trigger, and view, and it copies freely between 32-bit and 64-bit machines and between big-endian and little-endian ones. The library is under 900 kibibytes with every feature enabled, a database can reach 281 terabytes, and the US Library of Congress lists the format as a recommended storage format.

---

# 04_layer_stack

So what is inside that library? SQLite compiles SQL into bytecode and then runs that bytecode on a virtual machine, and the code is organised as one stack of eight layers. At the top is the interface. The next three layers, tokenizer, parser, and code generator, form the SQL compiler. The bytecode engine, the VDBE, executes the program, and together with the interface it forms the core. Below it, the backend has three layers: the B-tree, the pager or page cache, and the OS interface, called the VFS. In API terms, sqlite3 prepare v2 is the compile step that produces a bytecode program in a sqlite3 statement object, sqlite3 step runs it on the virtual machine, and the backend stores everything as B-trees made of fixed-size pages. We will now walk down this stack, compiler first.

---

# 05_compile_path

Here is the top half of the stack, layers two to four, highlighted on the rail. Take one statement, a select with a bound parameter. The tokenizer, hand-coded in tokenize.c, splits the text into tokens, and here is a detail worth remembering: in SQLite the tokenizer calls the parser, the reverse of the YACC and Bison habit, which makes it thread-safe and faster. The parser gives tokens meaning from their context; it is generated by the Lemon parser generator from parse.y, and it is reentrant, thread-safe, and does not leak memory on syntax errors. The code generator walks the parse tree and emits bytecode; the files where.c and select.c form the query planner, which picks among possibly millions of ways to compute the answer. All of that is what sqlite3 prepare v2 does. The result is one bytecode program in a sqlite3 statement object, and sqlite3 step runs it on the VDBE until it finishes, produces a row, hits a fatal error, or is interrupted.

---

# 06_storage_path

Now the bottom half of the rail, layers six to eight. The B-tree layer asks for a page by number, the pager caches pages and provides rollback, atomic commit, and file locking, and the VFS does the actual reads and writes on the operating system's file. Every read and write is a whole page, 4096 bytes by default, and the page size can be any power of two from 512 to 65,536. This strip is one B-tree page in file order: a 100-byte database header that exists only on page one, an 8-byte header for leaf pages or 12 bytes for interior pages, the cell pointer array growing forward, unallocated space, the cell content area growing back from the end, and a reserved region that is usually empty. An interior page holds K keys and K plus one child pointers. Table B-trees use a 64-bit signed rowid key and keep data only in the leaves; index B-trees use arbitrary keys and store no data. There is one B-tree per table and per index, all in the same file, with the schema table rooted at page one. About 4.29 billion pages of 64 kibibytes is where the 281 terabyte limit comes from, and every valid file begins with the string SQLite format 3.

---

# 07_journal_vs_wal

Pages have to change atomically, even if the power fails, and SQLite has two ways to do it. The default is the rollback journal: first copy the original pages into a separate journal file, then write the changes directly into the database. The commit happens at the moment the journal file is deleted, and if the process crashes or rolls back, the journal is played back into the database to restore it. Since version 3.7.0, released in July 2010, there is the write-ahead log, which inverts the idea. The database file is left alone, the writer appends the changed pages to a separate WAL file, and a commit is simply a commit record appended to that log. Because the database file is never touched to commit, readers can keep using the original while commits proceed.

---

# 08_wal_concurrency

Let's zoom into that WAL file. Frames are appended in order by the single writer. When a read transaction starts, it remembers the last valid commit record as its end mark, so each reader sees one consistent snapshot even while the writer keeps appending. A reader takes the newest copy of a page that appears before its own end mark, otherwise it reads the database file, and a shared-memory wal-index makes that lookup fast. That shared memory is also why every process must be on the same host. Eventually a checkpoint copies WAL pages back into the database, stopping at the oldest active reader's end mark, which is why one long-running reader can stall it. By default this happens automatically once the WAL reaches 1000 pages, and when everything is checkpointed and idle the WAL rewinds to its start. The payoff is real: WAL is significantly faster in most scenarios, readers and the writer run concurrently, disk I/O is more sequential, and there are far fewer fsync calls. The costs are that it works only on one host and not over a network filesystem, it adds the wal and shm files beside the database, it can be one or two percent slower for read-mostly work, and it prefers small transactions, so rollback modes suit transactions beyond roughly a hundred megabytes.

# 09_testing_culture

Why trust a library that sits in a trillion places? Look at the testing. As of version 3.42.0, the library is about 155.8 thousand lines of C, and the project carries about 92 million lines of test code and test scripts, roughly 590 times as much. The two squares are drawn to scale. That test effort is split across four independent harnesses. The TCL tests are the primary suite during development, with 51,445 distinct test cases that expand to millions of runs. TH3 is a proprietary harness of about 1,055 thousand lines of C that delivers 100 percent branch coverage and 100 percent MC/DC coverage of the core, the coverage level behind what sqlite.org calls aviation-grade testing. SQL Logic Test runs 7.2 million queries and checks that SQLite gives the same answers as PostgreSQL, MySQL, SQL Server, and Oracle 10g. And the dbsqlfuzz fuzzer runs about a billion mutations a day, mutating SQL and the database file together. On top of that come out-of-memory, I/O error, crash, and power-loss tests, and a pre-release TH3 soak of about 248.5 million tests.

---

# 10_public_domain

The second trust factor is legal, and it is the simplest one in this deck: there is no license to comply with. In the project's own words, anyone is free to copy, modify, publish, use, compile, sell, or distribute the original SQLite code for any purpose, commercial or non-commercial, and by any means. That holds because every author signs an affidavit dedicating their work to the public domain, with the originals kept in a firesafe at Hwaci, and because every line is written from scratch and traceable to its author. The consequence is that SQLite is open-source but not open-contribution: no patch is accepted without such an affidavit. And for organisations in places that do not recognise the public domain, Hwaci sells a Warranty of Title, and the proceeds fund SQLite's continued development.

---

# 11_when_to_use

So when should you reach for it? The official checklist is three questions, asked in order. First, is the data separated from the application by a network? If so, choose a client/server engine, because the high-bandwidth link between engine and disk should not cross the network. Second, do many writers need to write at the same instant without queuing? SQLite allows unlimited readers but one writer at a time, and since a write usually takes milliseconds, writers can often take turns, but if they cannot, use client/server. Third, will the data outgrow one file? The limit is 281 terabytes, and long before that a centralised server is worth considering. If the answer to all three is no, choose SQLite. That covers a lot of ground: embedded and IoT devices, application file formats, websites under about 100,000 hits a day, data analysis, caching enterprise data, server-side databases such as one database per user, data transfer, archives, and internal or temporary databases. And that 100,000 figure is conservative; SQLite has been shown to handle ten times that traffic.

---

# 12_closing

Put it together and the opening line makes sense: SQLite competes with fopen, not with Oracle. It is in-process, one ordinary file, with zero configuration. Its test code is 590 times the size of the library, with 100 percent branch and MC/DC coverage. And it is in the public domain, free for any purpose with no license. So the takeaway for us is practical: wherever you would have reached for fopen and a home-grown file format, reach for SQLite instead. Or, as the project's motto puts it: small, fast, reliable, choose any three.
